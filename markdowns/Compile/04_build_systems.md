# Build Systems: Make, Autotools, CMake, Meson, and Ninja

A C or C++ program needs a compiler and linker, but a project also needs to
describe its source files, dependencies, options, generated files, tests, and
install rules. Build systems automate that work. The tools in this guide
overlap, but they do not all operate at the same level: CMake and Meson describe
projects and generate a build graph, while Ninja executes a graph generated for
it.

## A short history

| Tool | Origin | The problem it addresses |
|---|---|---|
| `make` | First developed by Stuart Feldman at Bell Labs in 1976 | Express dependencies and shell commands as rules, then rebuild only outputs whose prerequisites changed. |
| GNU Autotools | Autoconf, Automake, and Libtool grew into a toolchain during the 1990s | Generate configure scripts and Makefiles that help source packages adapt to different Unix-like systems and toolchains. |
| CMake | Began at Kitware in 2000 | Describe a project once and generate build files for different native build tools and IDEs. |
| Ninja | Created by Evan Martin in 2012 | Execute a build graph quickly with a compact build-file format; it is commonly generated by CMake or Meson. |
| Meson | Began in 2012, created by Jussi Pakkanen | Provide a concise project description, built-in dependency handling, and fast builds; Ninja is its usual backend. |

These dates mark the projects' origins, not the point at which their current
feature sets were complete. Each tool has continued to evolve. The list is not
a ranking: established projects continue to use different tools for different
portability, integration, and maintenance requirements.

## The layers are different

A useful way to compare these tools is to separate the project description from
the build executor:

| Tool | Project description | Build execution |
|---|---|---|
| Make | Rules and recipes are written directly in a Makefile. | Make evaluates prerequisites and runs recipes using a shell. |
| Autotools | `configure.ac` and `Makefile.am` describe feature checks, generated Makefiles, and portable source distributions. | The generated `configure` script selects settings; Make executes the generated rules. Libtool helps manage portable library builds. |
| CMake | `CMakeLists.txt` describes targets, dependencies, options, tests, and install rules. | A generator writes Ninja files, Makefiles, or native IDE project files; the selected tool executes them. |
| Meson | `meson.build` describes targets, dependencies, options, tests, and install rules. | Meson typically generates Ninja files, then `meson compile` invokes Ninja. Other backends are available. |
| Ninja | It is not normally the high-level project description. Its build file lists an explicit dependency graph and commands. | Ninja runs that graph and focuses on fast incremental builds. |

This explains why “CMake vs Ninja” is not always an either/or choice. A project
may use CMake to describe targets and Ninja to build them. Meson and Ninja are
commonly paired in the same way. Make can be used directly, or as a backend
generated by CMake.

## Choosing a tool

- Use **Make directly** for a small project or when the build rules themselves are the subject. Rules are explicit and widely understood, but complex projects can accumulate shell-specific logic and global variables.
- Use **Autotools** when maintaining a source distribution whose configuration needs to probe many Unix-like platforms and older toolchains. Its generated `configure` script is designed to let users configure a release without needing the original Autotools development environment.
- Use **CMake** when a project needs broad compiler, operating-system, and IDE support, or when downstream packages already expect CMake targets and package configuration.
- Use **Meson** when a project benefits from a concise, target-oriented description and its supported platform and dependency workflows fit the project.
- Use **Ninja** as an executor when fast incremental builds are useful and a higher-level build system can generate its build graph.

No build system makes a project portable by itself. Portability also depends on
the compiler, system libraries, shell commands, filesystem behavior, and
assumptions in the build rules. Prefer target-based dependencies and standard
tools, then validate on each supported platform.

## Why Makefiles differ across operating systems

The dependency-and-recipe model is portable, but a Makefile's commands and
extensions may not be. GNU Make, BSD Make, and Microsoft's `nmake` do not
implement identical language features. Even when the Makefile syntax is
accepted, a recipe may assume Bash, a POSIX utility, a particular compiler
command, or a Unix path convention that is unavailable on another host. Windows
projects may also use different shells, path handling, compilers, linkers, and
library layouts.

To make a direct Makefile more portable:

- Keep recipes simple and use a clearly specified Make implementation.
- Avoid relying on one shell's syntax unless the project requires and documents that shell.
- Use variables for compiler and tool names, and avoid hard-coding machine-specific paths.
- Separate platform-specific flags and commands instead of assuming they are universal.
- Test the build on every supported operating system and toolchain.

Higher-level systems such as CMake and Meson can abstract many generator and
compiler differences, but they cannot remove platform-specific code or missing
dependencies from the project itself.

## Try both build descriptions in this repository

This repository uses the same Docker toolchain image for CMake and Meson/Ninja. The host needs Docker and GNU Make; compilers and build tools are installed in the container.

```sh
make build
make test

make meson-build
make meson-test
```

Inside `make shell`, the generated build steps are visible directly:

```sh
cmake --preset debug
cmake --build --preset debug

meson setup build/meson/debug --buildtype debug
meson compile -C build/meson/debug
```

The repository's [CMake tutorial](02_modern_cmake.md) and [Meson tutorial](03_meson.md) explain the two project descriptions in detail.
